# Architecture

## Overview

A single backend, with **WhatsApp (via OpenClaw + an LLM agent)** as the primary interface for crews and management, and a **web dashboard** for anything that genuinely needs a screen (bulk setup, reports).

```
Crew / Management phone (WhatsApp)
        ↕
OpenClaw gateway (self-hosted, WhatsApp channel, QR-paired)
        ↕
Agent (DeepSeek → Kimi → OpenAI → Gemini → Claude fallback chain — tool-use enabled)
   ── Speech-to-text (voice notes, live via OpenAI gpt-4o-transcribe) ── Image classification (live via OpenAI gpt-4o — see below; OCR/amount-extraction still not built)
        ↕
Backend API (REST)
        ↕
Postgres  +  WhatsApp shared location (live + one-time pins) for real-time position — POC phase, no hardware
        ↕
Web dashboard (management) + Map view — v1 built: login + live vehicle-location map (see openclaw/README.md and docs/DEPLOYMENT.md#dashboard-auth-rollout). Additional screens (ops overview, inventory browser, reports) not yet built. Crew members now get dashboard access too, via a separate WhatsApp magic-link login (see below) rather than email+password.
```

Outbound material orders don't hit a vendor API directly — the agent compiles the order details and sends them to `info@thesodboys.ca` (or straight to whoever's picking it up), for a human to actually contact the vendor. See [DATABASE_SCHEMA.md](DATABASE_SCHEMA.md) for the `purchase_orders` status flow.

## Design principles

1. **Crew-facing = scan/text/photo, almost no typing.** Loadouts check out with one QR scan; corrections happen through natural language, not forms.
2. **Management-facing = dashboard + WhatsApp queries.** Anything that needs a quick answer ("who has the compactor") goes through chat; anything that needs a screen (reports, template editing) goes through the dashboard.

**Crew dashboard access.** Every crew member now has *some* dashboard view, not just management/admin — but true to principle 1, getting there is still "almost no typing": a crew member asks the agent for the link over WhatsApp, gets a login link back (`send_dashboard_login_link`, 15-minute expiry, redeemable more than once in that window, capped at one fresh link per crew member per 10 minutes), taps it, and lands in a small scoped view of their own pay, jobs/shifts, checkouts, and spend claims (`/me/*` routes, `backend/src/routes/me.ts` — see [API.md](API.md#my-stuff-crew-self-service)). This is a genuinely separate auth path from the dashboard's email+password login (`sessions` is dual-path as of `0051`/`0052` — see [DATABASE_SCHEMA.md](DATABASE_SCHEMA.md#dashboard-auth)), and a genuinely separate frontend surface (`CrewPortalPage`, not a cut-down version of the admin `Dashboard`). This is also the first place in the API that does row-level scoping server-side (deriving the caller's identity from their session, never a client-supplied id) rather than trusting a client-supplied `crew_member_id` filter like every other dashboard route does. The link itself is always delivered by DM to the resolved sender's own number, never as a reply inside a group — a real gap found and fixed 2026-08-16: since links are reusable for 15 minutes rather than single-use, answering a group request in the group would post a live, tappable login link where anyone else in that group could use it. See `AGENTS.md`'s "Sending a crew member a dashboard login link".

`foreman`'s "a little more" is built, scoped concretely (site roster, site checkouts, site orders, all read-only, scoped to wherever *the caller themselves* has a confirmed shift today). `management`/`owner`-role crew sessions reach the same three sections but with a genuinely broader scope, not a relabeled copy of foreman's — corrected 2026-08-16 after review found both tiers were running the identical self-scoped query: every site with a confirmed shift today, org-wide, not just the caller's own (`resolveVisibleSiteIds` in `backend/src/routes/me.ts`). A real `users` account (`role: 'staff'` or higher) remains the recommended path for anyone who wants the full admin-adjacent dashboard rather than this crew-session tier — that's unchanged.
3. **Confirm before execute.** Any agent action that moves inventory, money, or a schedule gets echoed back for a yes/no before it commits. This is non-negotiable — a misheard voice note should never silently move equipment or place an order. For seven specific actions — hours (`log_timeclock_event`), material-usage claims (`adjust_consumable_quantity`), damage/condition claims on returns (`return_checkout`), mileage claims (`submit_mileage_claim`), asset condition claims (`verify_asset`), delivery-receipt claims (`mark_purchase_order_fulfilled`), and shift-extension requests (`request_shift_extension`, added 2026-08 — an extension changes payroll hours, same "not independent verification of itself" reasoning as the other six) — the crew member's confirmation alone is no longer enough: these route through `pending_confirmations` (see [DATABASE_SCHEMA.md](DATABASE_SCHEMA.md#confirmations)) and also need management's sign-off before they take effect, since a crew member confirming their own claim isn't independent verification of anything. This is a **pilot** on the self-reported physical-reality/money claims that most needed it, not a cutover of the agent's other ~71 mutating tools, which stay single-party for now. Management can act from either channel — the dashboard, or WhatsApp directly (a crew member whose `role` is `management` or `owner` can approve/reject via the agent; anyone else is refused). See [DATABASE_SCHEMA.md](DATABASE_SCHEMA.md) for the full 5-tier role hierarchy (`crew`/`foreman`/`yard`/`management`/`owner` on the WhatsApp side, `admin`/`staff`/`owner` on the dashboard side) and where each tier's permissions and response depth differ.
4. **The system notices first.** Idle crews, wrong-site arrivals, stalled orders — the exceptions engine compares expected state against actual state continuously and raises a flag before a person has to complain. See [EXCEPTION_HANDLING.md](EXCEPTION_HANDLING.md).
5. **Nothing gets assigned that isn't confirmed to exist.** An asset with no verification record is treated as unconfirmed, never assigned by the loadout engine. See the bootstrap audit process below.
6. **No direct vendor ordering, deliberately, for now.** The agent prepares information; a human sends it. This can change in a later phase once the manual workflow is proven.

## Inventory bootstrapping

There's real equipment and material history scattered across past job sites, trucks, and the crew's storage unit — none of it starts out in the system. The rule: **the loadout engine only ever assigns what's been confirmed to exist.** An asset without a verification timestamp is unconfirmed, not available, and a loadout that needs it shows a shortfall instead of silently proceeding.

Bootstrapping is a physical sweep (Access Storage, active sites, trucks) tagging every asset with a QR code, condition, and status — split across the crew as part of normal days rather than one big shutdown-and-count event. Full detail in [DATABASE_SCHEMA.md](DATABASE_SCHEMA.md#assets) under the `assets.status` / `last_verified_at` fields.

## WhatsApp chat-history import

`backend/src/db/importWhatsappHistory/` reconstructs real crew/site/schedule history from an exported WhatsApp chat transcript, ahead of a demo/launch — a one-time backfill, not a recurring sync. Three confidence tiers, deliberately treated differently:

- **Tier 1 (roster)** — high confidence: WhatsApp's own system messages ("X added Y", "X was removed") parsed mechanically with real timestamps, cross-referenced against owner-supplied screenshots for phone numbers. `applyRoster.ts` writes this straight to `crew_members`, everyone imported at role `crew` by default (promoted afterward via the Crew page).
- **Tier 2 (sites)** and **Tier 3 (dispatch-derived shifts, presence cues, checkout candidates)** — medium/low confidence: real addresses and shift-like dispatch messages, but never auto-inserted by the dry-run pipeline itself (`siteExtractor.ts`/`activityInference.ts`'s own header comments are explicit about this) — `run.ts` only ever produces a markdown review report for the owner to confirm. `applyActivity.ts` is the write counterpart, run only after that review: sites and dispatch-derived shifts (plus a paired `timeclock_entries` "in" row, tagged `import_source = 'whatsapp_history_import'` for provenance — see [DATABASE_SCHEMA.md](DATABASE_SCHEMA.md)) get written; checkout candidates never do, since `checkouts.asset_id` is a required foreign key and the extracted data is just a freeform tool keyword in message text, nothing to actually point at.

Neither apply script is meant to run twice against a live-in-use database — they were written for a one-time reset, not an idempotent recurring job (`applyRoster.ts` guards duplicate phones with `ON CONFLICT DO NOTHING`; `applyActivity.ts` has no equivalent guard for sites/shifts).

## Management notifications

Principle 4 ("the system notices first") originally only meant alerts sat in Postgres until someone asked (`list_alerts`) or a fixed-time digest cron read them out. As of 2026-08, genuine exceptions push to management on WhatsApp within a minute of happening, without waiting for a digest — a tool marked missing/retired, a vehicle outside its geofence, an overdue checkout, or a stalled order. Everything else (normal registration/verification, routine order progress, idle-crew flags) stays digest-only, to avoid turning this into a stream of pings once real crew are onboarded.

This couldn't be built as "the backend calls OpenClaw directly," because it structurally can't: the backend runs in its own Docker container with no filesystem access to the `openclaw` binary (a native systemd service on the Pi host, not in `docker-compose.yml`) and no network path to the gateway (loopback-bound on the host, not reachable from inside the container). So the flow keeps the one direction that already works everywhere else in this system — OpenClaw calling the backend's HTTP API, never the reverse — just inverted into a poll instead of a push:

```
Backend route/worker detects an event
        ↓ (writes a pre-formatted message)
Postgres `notifications` table (priority: critical | routine)
        ↓ (polled every minute, host-side)
openclaw/notifier/deliver-notifications.mjs  (runs as an `openclaw cron --command` job, on the Pi host)
        ↓ (critical only — routine rows are pulled separately by the digest agent's list_notifications tool)
openclaw message send --channel whatsapp     (direct send per recipient, no LLM call)
        ↓
Everyone with role `management` or `owner` (queried from crew_members fresh each run)
```

Recipients are queried by role, not a fixed number — `GET /crew-members?role=management&active=true` plus the same for `owner`, deduped by phone. Registering a second management/owner crew member picks them up automatically, no config change needed. `foreman` is deliberately excluded from critical paging for now — nothing site-scopes an alert to "their" site today, so paging every foreman for every critical alert everywhere would be noisy; a one-line change once that changes. One `notifications` row still means one `delivered_at`/`whatsapp_message_id`/`acknowledged_by` even with multiple recipients — whoever acknowledges first (on any recipient's phone) clears it for the whole team, "management as a unit" semantics carried forward from when there was only ever one recipient, not a new gap. The 3 digest cron jobs (morning/midday/evening) now deliver to the crew WhatsApp **group** — `delivery.to` is a single group JID, since OpenClaw's own cron primitive is single-destination by construction (the same limitation that keeps this script's own multi-recipient fan-out from happening at the cron level). Group content is deliberately least-privileged (shift/coverage facts, no financials or named issue detail) since the whole crew reads it. The full-detail version management/owner/IT still need no longer goes out unreviewed mid-turn: the agent's `send_role_digest` tool was replaced (2026-08) by a `create_message_draft` / `list_pending_message_drafts` / `resolve_message_draft` review queue (`message_drafts` table — see [DATABASE_SCHEMA.md](DATABASE_SCHEMA.md#confirmations)) — every proactive, agent-initiated digest is written as a pending draft first, and only actually sent once IT (Redji) reviews and approves it via the agent. Ordinary conversational replies are explicitly exempt from this gate — only agent-initiated broadcasts (digests, role pings) go through it, since gating every interactive reply behind manual approval would make live WhatsApp use unworkable. See `AGENTS.md`'s "Scheduled digests: group vs. DM".

If a critical notification is delivered but nobody acknowledges it within 20 minutes, the same script's second pass re-sends it to everyone in the recipient list (capped at 3 escalations) — see `GET /notifications/escalation-candidates`. Acknowledgment itself happens from a WhatsApp reply, resolved by the agent via `list_notifications`/`acknowledge_notification` (see `AGENTS.md`'s "Acknowledging critical notifications"), or from the dashboard's activity feed — either way it's tracked entirely on the `notifications` row and deliberately never touches `alerts.resolved_at`: "seen, on it" and "actually fixed" are different states.

A second, separate script (`openclaw/notifier/nudge-shifts.mjs`, its own daily cron job) follows the same "poll the backend, push via `openclaw message send`" shape but targets a crew member directly rather than management — reminding them to confirm tomorrow's shift the evening before, rather than waiting for them to forget. A third script, `openclaw/notifier/shift-reminder.mjs` (added 2026-08, every 10 min), is a distinct notification rather than a variant of the nudge — it only fires for shifts already `confirmed`, targets the ~60-minute window before `start_time`, and exists to catch the "forgot it was starting soon" case a once-daily evening-before nudge can't cover. Both track their own idempotency column on `shifts` (`nudged_at`, `reminder_sent_at`) since they're independent notifications that can legitimately both fire for the same shift on the same day.

See `openclaw/notifier/README.md` for all scripts and their cron jobs, and [DATABASE_SCHEMA.md](DATABASE_SCHEMA.md#notifications) for the table.

## IT monitoring and escalation

Added 2026-08-16. Distinct from management notifications above in one load-bearing way: those alerts require the backend to already be up (something writes a row to `notifications`, and the poller reads it back out). `openclaw/notifier/heartbeat.mjs` (every 2 min, host-side) exists specifically for the case that assumption breaks — if the backend or Postgres itself is down, nothing can write an alert row *about* that, so this script checks `/health` and a direct `docker exec` into Postgres, and on failure messages WhatsApp *directly*, bypassing the `notifications` table entirely. Connectivity (registry/DNS reachability) and disk-space checks go through the normal alert pipeline instead, since the backend being up is exactly what makes those checks possible to record and act on before they get worse.

New alert types: `connectivity_degraded`, `disk_space_low`, `it_issue`, `system_offline`. Recipients for these route through `notification_settings.it_escalation_roles` (default `{owner}`), a `recipient_roles_override` on the `notifications` row itself (see `backend/src/lib/notify.ts`) rather than the broader `critical_notification_roles` broadcast — an infra problem needs one specific person looking at it, not the whole management group getting paged for something they can't act on. Crew can escalate a problem directly via `report_it_issue` (WhatsApp tool, no confirm-before-execute, same reasoning as `report_safety_incident`) — see `AGENTS.md`'s "Escalating an IT issue".

`crew_members.role` gained a sixth value, `IT`, for the person actually operating the system — kept distinct from `management` specifically so `it_escalation_roles` can target them without also sweeping them into every broader management-tier operational broadcast unrelated to running the system itself. See [DATABASE_SCHEMA.md](DATABASE_SCHEMA.md#crew_members) for the full role list.

## Photo classification

`fieldops-media`'s hook still auto-files every inbound WhatsApp photo instantly as `documents.type = 'photo'` — unchanged, zero added latency for the crew member. Separately, `tools.media.image` (OpenClaw's built-in vision-understanding capability, same mechanism as the voice-transcription feature above) is turned on, so the agent turn that follows also sees a text description of the photo and can call `classify_document` to upgrade the type to `receipt`/`permit`/`contract`/`insurance_cert`/`disposal_ticket` once the image content makes that clear — `photo` is left as-is for anything else (equipment, damage, job-progress shots), since there's no more specific type for those.

The bridge between "the hook knows the new document's id" and "the agent turn can act on it" doesn't go through the normal reply pipeline — `message:received` (the hook fieldops-media already used) is fire-and-forget and can't inject anything into a prompt. Instead it hands the id off via a short-lived, session-keyed in-process map, picked up by a second, *typed* hook (`agent_turn_prepare`, registered via `api.on(...)`) that appends a line naming the pending document id into that turn's prompt. Entries are consume-once and TTL-bounded, since "one message maps to exactly one agent turn per session" isn't a documented platform guarantee — worst case on a mismatch is a wrong `type` on one document, corrected the same way any other misclassification would be.

No confirmation round-trip for the `classify_document` call itself — it corrects metadata on a record that was already auto-filed, it doesn't create anything new or move inventory/money/schedule, so it stays consistent with the hook's existing no-confirmation behavior. See `AGENTS.md`'s "Photo classification" section for the agent-facing rules, and [DATABASE_SCHEMA.md](DATABASE_SCHEMA.md#documents) for the now-mutable `type` column.

## Carpool

Added 2026-08, request-based rather than auto-matched — no rider/driver concept existed anywhere before this (`trips.driver_id` was singular, no seats field on `vehicles`, zero prior mentions of carpool/rideshare in the schema). A crew member posts a `need_ride` or `offering_ride` row via the agent (`create_ride_request`, informational confirm-back but not a `pending_confirmations` gate — coordination, not money/inventory/schedule, same tier as `log_vehicle_location`); matching a specific pair is a human decision made explicitly via `match_ride_requests`, not automatic, which sets `matched_request_id` on both `ride_requests` rows in one transaction. No compensation tracking for now — that's a deliberate scope cut, not a gap to be filled implicitly later. Live tracking for a matched ride reuses Part 3's location data directly rather than a new mechanism: `get_ride_driver_location` resolves the matched offer's driver and checks their `crew_telemetry`, falling back to `vehicle_telemetry` if they have an assigned vehicle instead. The dashboard's `CarpoolPage` is read-only (open requests by date, two columns) — matching stays a WhatsApp/agent action, the same "screen for browsing, chat for doing" split as the rest of principle 2.

## Hosting (POC)

Self-hosted on a Raspberry Pi 5 (8GB), via Docker Compose — Postgres, backend API, and OpenClaw as separate services. Exposed through **Cloudflare Tunnel** rather than router port-forwarding, so nothing on the home network accepts inbound connections directly. Runs off a USB SSD, not the microSD card — sustained Postgres writes wear microSD out quickly. Nightly `pg_dump` backup to a second location. Migrating to a small VPS later is a same-`docker-compose.yml` move if this graduates past POC. Full setup in [DEPLOYMENT.md](DEPLOYMENT.md).

Running a **named Cloudflare Tunnel** on a real domain (`dashboard.sodboysltd.org`, switched over 2026-08-16 from the earlier Quick Tunnel mode) — a stable, permanent URL instead of a new random one on every restart. `--protocol http2` is forced (rather than the default QUIC/UDP) after confirming live that this host's connection was dropping every ~8-13 minutes with QUIC specifically — a home router's UDP NAT table timing out an idle connection, a failure mode HTTP2's TCP transport doesn't have. See [DEPLOYMENT.md](DEPLOYMENT.md)'s Cloudflare Tunnel section for the full setup.

Even with a stable URL, the tunnel itself can still drop or the backend/Postgres/network underneath it can degrade — two separate monitoring layers cover that: `openclaw/notifier/sync-dashboard-url.mjs` (every 5 min) polls the dashboard's own reachability, keeps a live URL cached in Postgres (`dashboard_url` table) for the agent's `get_dashboard_url` tool, and raises a `dashboard_unreachable` alert if it's down; `openclaw/notifier/heartbeat.mjs` (every 2 min, added the same day) covers the broader case the URL check can't — backend/Postgres/disk/connectivity itself failing — and is the one thing in this system that messages WhatsApp *directly*, bypassing the normal `notifications` table pipeline entirely, since a backend-down alert can't ask the backend to record itself. The agent can also restart the tunnel directly on request (`restart_dashboard_tunnel`) — the one tool in `fieldops-tools` that shells out to `docker` on the host instead of calling the backend, since the OpenClaw gateway runs as a native systemd service on the Pi, not a container, and already has that access.

## Model provider

A 5-provider fallback chain, cheapest to most expensive, each one only tried if the previous fails or times out: **DeepSeek** (`deepseek-chat`) → **Kimi/Moonshot** (`kimi-k2.6`) → **OpenAI** (`gpt-5.4-mini`) → **Gemini** (`gemini-2.5-flash`) → **Claude** (`claude-sonnet-5`). DeepSeek handles the large majority of dispatch/ordering/status traffic at near-zero cost; everything after it is pure resilience — a provider outage or rate limit shouldn't take the agent down, and each fallback step also happens to run on different underlying infrastructure than the one before it. Configured per-agent (scoped to the `fieldops` agent specifically, not the personal `main` agent) via `openclaw models set` / `openclaw models fallbacks add` — see `openclaw/openclaw.config.example.json`.

## Location strategy (POC)

WhatsApp shared location (live location for continuous tracking, one-time pins for point-in-time check-ins) is the sole real-time position source for the POC — no OBD hardware yet. This depends on people actually sharing live location, which is a real behavior change worth reinforcing at onboarding (only 6 location shares happened across 10 weeks of the real chat history this system was designed from). OBD telemetry remains a future upgrade once the workflow is proven.

**Person-level location (added 2026-08).** Until now, live location only had a path into the system via `vehicle_telemetry` — a crew member with no assigned vehicle had nowhere for a location share to go. `crew_telemetry` (mirroring `vehicle_telemetry`'s shape exactly) closes that gap: a location share now logs to it via `log_crew_location`, in addition to `log_vehicle_location` when the sender also has an assigned vehicle — both can be true for the same share. The exceptions worker's `checkCrewLocationStale` runs alongside `checkWrongSite` on the same tick: for each crew member on a `confirmed` shift today, a latest telemetry point older than `notification_settings.crew_location_stale_minutes` (default 90) raises `crew_location_stale`, and a point outside the shift's site geofence raises `crew_off_site` — both routed to `it_escalation_roles`, a safety/location concern rather than a broad management broadcast.

**Geofence verification (added 2026-08).** `sites.center_lat/lng` and `geofence_radius_m` existed since the first migration but `timeclock_entries.geofence_verified` was purely agent-asserted — never independently checked against real coordinates. `POST /timeclock` and `approveTimeclockEvent` now compute it server-side (`resolveGeofenceVerified`, reusing the same `haversineDistanceMeters` helper `checkWrongSite` already uses) from optional `lat`/`lng` passed alongside a clock-in; no coordinates or no site geofence configured both resolve to `false`, never a client-supplied assertion. This is verification-only, deliberately — it doesn't auto clock in/out on geofence entry/exit, and like `checkWrongSite`, it's circular-radius only (polygon sites stay unchecked, the same documented gap as [EXCEPTION_HANDLING.md](EXCEPTION_HANDLING.md)).
