# openclaw/

OpenClaw gateway configuration and agent tool plugins.

**A note on how to read this file:** most of the sections below narrate the *first build* of each piece (2026-08-12/13), including status claims and blockers ("not yet verified", "pending real model keys") that were true then and are long resolved now — kept as-is because the debugging narrative is genuinely useful, not because the system is still in that state. For **current** status, tool count, and everything built after 2026-08-13 (role hierarchy, dashboard v2+, two-party confirmations, crew dashboard access, IT monitoring, geofencing, live location, shift extension, carpool, the message-draft review queue), see [../CHANGELOG.md](../CHANGELOG.md) and [../docs/ARCHITECTURE.md](../docs/ARCHITECTURE.md) — this file was not kept current line-by-line across that whole build.

OpenClaw is a CLI tool (`curl -fsSL https://openclaw.ai/install.sh | bash`), not a Docker service — it runs as a native systemd user service on the host. See [../docs/DEPLOYMENT.md](../docs/DEPLOYMENT.md) for the real install/run steps. `docker-compose.yml` only manages Postgres and the backend.

- `openclaw.config.example.json` — reference config, verified against a real running OpenClaw 2026.7.1-2 instance (`openclaw config schema` / `openclaw config get`), not just docs. Set `tools.profile` to `messaging`, not the `coding` default — this agent talks to crew over WhatsApp, it shouldn't have shell/file/coding tools. Don't hand-edit API keys into a config file; use `openclaw onboard --deepseek-api-key <key> ...` or `openclaw config set` so credentials go through OpenClaw's own secret handling.
- `plugins/fieldops-tools/` — the agent tool plugin mapping the backend API ([../docs/API.md](../docs/API.md)) to callable tools, built with OpenClaw's `defineToolPlugin` SDK (`openclaw plugins init --type tool`). Started at 50 tools (2026-08-12); **now 76 tools** across every API.md group, including geofence-verified check-in, crew/vehicle live location, shift extension, carpool coordination, and the message-draft review queue — see [plugins/fieldops-tools/README.md](plugins/fieldops-tools/README.md) for the current full list, grouped by category, and `src/index.test.ts` for the exact declared order (hand-maintained — update it in the same change that changes the tool list). Built, `npm run plugin:build && npm run plugin:validate` passing, installed with `openclaw plugins install ./plugins/fieldops-tools --link`, and every tool smoke-tested end to end against the real backend — including every business-rule guard (forward-only order/transfer status, illegal timeclock transitions, wrong-site transfer rejection, PO send/fulfill state machine, damaged-checkout routing to in_maintenance).
- `plugins/fieldops-media/` — hook-only plugin (no agent tools) that auto-logs inbound WhatsApp photo attachments as documents, bypassing the agent turn entirely. Uses `definePluginEntry` + `api.registerHook("message:received", ...)` rather than `defineToolPlugin`, since tool plugins have no hook-registration surface. Resolves the sender's phone to a crew member via `GET /crew-members?phone=`, uploads the already-downloaded local file via `POST /documents/upload`, tagged `auto-logged`/`whatsapp`. Built, unit-tested (`npm test`), installed (`openclaw plugins install`), and smoke-tested end to end by invoking the real `register()`/hook handler against the live backend — confirmed byte-identical file round-trip, correct skip behavior for unmatched senders, and correct no-op for non-image media (voice notes).
- `agent-workspace/` — the system prompt, as OpenClaw actually structures it: not a single string, but a workspace of instruction files (`AGENTS.md`, `SOUL.md`, `IDENTITY.md`, `USER.md`, `TOOLS.md`, `HEARTBEAT.md`). **Done.** Deployed to a dedicated **isolated agent** (`openclaw agents add fieldops`, its own workspace at `~/.openclaw/agents/fieldops/workspace` on the Pi) rather than overwriting the default `main` agent — `main` is OpenClaw's generic personal-assistant template (a companion with a name/vibe/emoji, "wake up and figure out who you are" onboarding, heartbeat/group-chat conventions); none of that fits a business dispatch tool, so `fieldops` gets entirely rewritten content instead. Covers: the confirm-before-execute rule from [../docs/ARCHITECTURE.md](../docs/ARCHITECTURE.md) (with the exact tool list it applies to), the business rules each tool enforces (so the agent doesn't fight the backend), the real crew vocabulary from [../docs/GLOSSARY.md](../docs/GLOSSARY.md), and an explicit list of what's NOT built yet so the agent doesn't imply capabilities it doesn't have.
- WhatsApp channel — **paired and bound.** The `whatsapp` plugin isn't bundled by default; installed via `openclaw plugins install @openclaw/whatsapp`, then `openclaw channels login --channel whatsapp` for the QR pairing (needs a phone present — not scriptable). Explicitly bound to the `fieldops` agent with `openclaw agents bind --agent fieldops --bind whatsapp`, confirmed via `openclaw agents bindings` (`fieldops <- whatsapp`) — without this, WhatsApp traffic would route to the personal `main` agent by default, not `fieldops`.
- Model provider — **working end to end as of 2026-08-12.** A 5-provider fallback chain, cheapest to most expensive: DeepSeek → Kimi (Moonshot) → OpenAI → Gemini → Claude (see [../docs/ARCHITECTURE.md](../docs/ARCHITECTURE.md#model-provider) for why). Scoped to the `fieldops` agent specifically via `openclaw config patch` against `agents.list` — `openclaw models set`/`fallbacks add` don't support `--agent`, they only touch global defaults, so a direct config patch was the only way to leave the personal `main` agent's model settings untouched.
- Voice-note transcription — **config live as of 2026-08-13.** Neither DeepSeek nor Anthropic (the two originally-funded providers) can transcribe audio, so a real OpenAI Platform API key was added (`openclaw models auth login --provider openai --method api-key` — the default `--provider openai` path is ChatGPT/Codex OAuth, not what a raw Platform key needs) and `tools.media.audio` was set to `{ enabled: true, models: [{ provider: "openai", model: "gpt-4o-transcribe" }] }` via `openclaw config set` (took effect without a gateway restart). OpenClaw handles inbound voice-note audio the same way it already does photos — no new plugin code needed, just this config. `AGENTS.md`'s confirm-before-execute rule already explicitly named "a misheard voice note" as a reason confirmation matters, so no prompt change was needed there beyond one line making it explicit that a transcript gets no special trust over typed text. **Not yet verified against a real inbound WhatsApp voice note** — same open gap as the rest of the WhatsApp round-trip (see `agent-tests/` note above); config-level checks (`openclaw models status --agent fieldops` showing `openai` off the missing-auth list) are the only verification so far.
- `agent-tests/` — grown from 12 scenarios to **14** since the first run below; send real messages to the real DeepSeek-backed agent (`openclaw agent --json`, no `--deliver` — nothing in this suite reaches a real WhatsApp chat, see `src/runAgent.ts`'s header comment) and assert on `toolSummary.tools` + real Postgres side effects, not exact reply text. Costs real tokens per run, not CI-scheduled. **First real run: 10/12 passed**, and the 2 failures were a genuine finding, not a test bug — `register_vehicle` was called immediately without waiting for confirmation in 2 runs, despite the explicit confirm-before-execute instruction (and despite following it correctly in a separate manual check minutes earlier). DeepSeek doesn't 100% reliably follow that rule for this tool; see [../docs/SECURITY.md](../docs/SECURITY.md)'s prompt-injection section for the fix and re-verification numbers. Both scenarios' cleanup correctly removed the resulting test vehicles either way — confirmed nothing leaked into real data. The suite has since also caught real non-determinism in which tool the agent picks for a given request (see [../CONTRIBUTING.md](../CONTRIBUTING.md)'s testing section) — an occasional flake here is informative, not necessarily a regression; re-run before concluding something broke.

  Three real bugs surfaced and got fixed on the way to a working reply, each only visible once the *previous* one was fixed (auth failures short-circuit before the next layer ever runs):
  1. **Missing provider plugins.** `deepseek`/`moonshot` are separate ClawHub packages, same as `@openclaw/whatsapp`, never installed. Fixed: `openclaw plugins install clawhub:@openclaw/deepseek-provider` / `clawhub:@openclaw/moonshot-provider`.
  2. **No real key.** The owner ran `openclaw models auth login --provider deepseek` themselves (never done by me — see repo-level policy on secrets) and pasted a real DeepSeek key. `openclaw models status --agent fieldops` confirmed `deepseek` off the "Missing auth" list.
  3. **`tools.profile: "messaging"` silently excludes plugin tools.** The first real model reply came back *honest but useless* — DeepSeek responded correctly, but said outright it had no `fieldops-tools` functions available and couldn't look anything up. Traced to OpenClaw's own `tool-catalog.js`: the `messaging` profile's allowlist is built from core tool ids only (`messaging: { allow: [...listCoreToolIdsForProfile("messaging"), "bundle-mcp"] }`) — it was never going to include a plugin's tools, regardless of how the plugin was installed. Fixed with `tools.alsoAllow` listing all 47 `fieldops-tools` tool names explicitly (see `openclaw.config.example.json`) — this adds on top of the `messaging` baseline rather than replacing it, so the original intent (no shell/coding tools for a WhatsApp bot) is preserved.

  Also hit and fixed a self-inflicted regression while chasing bug 1: re-running `openclaw plugins install` on `fieldops-tools` today (to pick up the new vehicle tools) created a second, redundant global registration alongside the original `plugins.load.paths`-based one from initial setup — a "duplicate plugin id" warning that looked cosmetic but actually broke tool resolution for cron/isolated-session turns specifically. Fixed by uninstalling the redundant `~/.openclaw/extensions/fieldops-tools` copy and restoring `plugins.load.paths`/`plugins.entries.fieldops-tools` via `openclaw config set`. **Lesson: `fieldops-tools` loads from the repo path — editing the repo and restarting the gateway is enough, never `openclaw plugins install` it again.**

  Verified with three real cron-triggered agent turns (the status digests), each producing correct, real-data replies and delivering successfully to WhatsApp — e.g. the morning digest correctly reported one unconfirmed shift and flagged it. Not yet tested via a live inbound WhatsApp message (task-tracked separately) — the cron path proves the model+tools+delivery pipeline end to end, but a real "someone texts the bot" round trip is still open.

## Status digests

Three `openclaw cron` jobs (not the per-agent heartbeat mechanism — see [agent-workspace/HEARTBEAT.md](agent-workspace/HEARTBEAT.md) for why) send a WhatsApp status summary at fixed times daily, DM'd to the owner's own number for the demo. Each triggers a normal `fieldops` agent turn that calls existing `fieldops-tools` tools (no new backend endpoint) and delivers the final reply via `--announce`:

| Job | Time | Prompt calls |
|---|---|---|
| `fieldops-digest-morning` | 6:00 AM America/Toronto | `list_shifts` (today), `list_alerts` (resolved=false) |
| `fieldops-digest-midday` | 12:00 PM America/Toronto | `get_crew_status`, `list_alerts` (resolved=false) |
| `fieldops-digest-evening` | 6:00 PM America/Toronto | `list_shifts` (today), `get_crew_status`, `list_overdue_checkouts`, `list_alerts` (resolved=false), `list_expiring_documents` (within_days=30) |

Verified at the time via `openclaw cron run <id> --expect-final` that the scheduler correctly fires the agent turn end to end — it failed only at the model-call step then (`model_not_found`/`No API key`, before real provider keys were added). Long since resolved: these have been running live daily since 2026-08-12, and as of 2026-08-16 the 3 digest jobs deliver to the crew WhatsApp group with least-privileged content, while the full-detail management/owner/IT version goes through the `message_drafts` review queue instead of sending directly — see [../docs/ARCHITECTURE.md](../docs/ARCHITECTURE.md)'s "Management notifications" for the current mechanism; the prompts below are the original single-DM versions, not what's live now.

Jobs live in OpenClaw's own cron store on the Pi (`openclaw cron list`), not in this repo, so they won't survive a Pi reprovision — recreate with:

```bash
openclaw cron add --name fieldops-digest-morning --display-name "Morning Dispatch Check" \
  --agent fieldops --cron "0 6 * * *" --tz America/Toronto \
  --channel whatsapp --to "<IT's real number>" --announce \
  --message "Morning dispatch check. Using list_shifts for today's date and list_alerts (resolved=false), summarize who is assigned where today, flag anyone not yet confirmed, and flag any unresolved alerts. Keep it brief, no filler."

openclaw cron add --name fieldops-digest-midday --display-name "Midday Status Check" \
  --agent fieldops --cron "0 12 * * *" --tz America/Toronto \
  --channel whatsapp --to "<IT's real number>" --announce \
  --message "Midday status check. Using get_crew_status and list_alerts (resolved=false), summarize where the crew currently is, explicitly call out anyone currently on break (get_crew_status's most recent event per crew member), flag anyone idle or off-site, and flag any unresolved alerts. Keep it brief, no filler."

openclaw cron add --name fieldops-digest-evening --display-name "End-of-Day Wrap-up" \
  --agent fieldops --cron "0 18 * * *" --tz America/Toronto \
  --channel whatsapp --to "<IT's real number>" --announce \
  --message "End-of-day wrap-up. Using list_shifts for today's date, get_crew_status, list_overdue_checkouts, list_alerts (resolved=false), list_expiring_documents (within_days=30), and list_notifications (routine events since this morning), summarize who worked today, explicitly call out anyone currently on break, anything still checked out, any tools registered/verified/sent to maintenance today, any job/order status changes, any unresolved issues, and any insurance/permit/cert documents expiring in the next 30 days. Keep it brief, no filler."
```

`list_expiring_documents` and `list_notifications` only got wired into the evening job, not morning/midday — both are once-a-day recap material, not something that needs repeating three times a day. Verified the underlying `GET /documents/expiring?within_days=30` endpoint still returns correctly (`200`, empty array — no test documents currently have an `expiry_date` set) via `openclaw cron edit` + a direct curl against the live backend; full digest content itself is still unverified pending real model keys, same blocker as everywhere else.

## Management notifications

Genuinely urgent events (a tool marked missing/retired, a vehicle outside its geofence, an overdue checkout, a stalled order) push to WhatsApp within a minute of happening — not via an agent turn (no LLM call at all, just `openclaw message send`), and not waiting for one of the three digests above. See [../docs/ARCHITECTURE.md](../docs/ARCHITECTURE.md#management-notifications) for why this has to be a poller on this side rather than the backend calling out directly (it structurally can't — no filesystem or network path from the backend's container to this host). Routine events (normal registration/verification, job progress, idle-crew flags) are deliberately excluded from instant push — they only show up in the evening digest above via `list_notifications`, to avoid flooding a phone once real crew are onboarded.

**Acknowledgment and escalation (2026-08-12):** a critical push that nobody acknowledges within 20 minutes gets re-sent, prefixed "⏰ Still needs attention", capped at 3 escalations. Acknowledging (via a WhatsApp reply, resolved by the agent's `list_notifications`/`acknowledge_notification` tools, or from the dashboard activity feed) is tracked separately from resolving the underlying alert — "seen, on it" isn't the same claim as "actually fixed." A new `vehicle_dark` alert type (a vehicle that was reporting telemetry today and has since gone quiet 3+ hours into a confirmed shift) ships as routine, not critical, for a burn-in period — telemetry is WhatsApp-share-driven and historically sparse (6 shares across 10 weeks of real crew chat), so this stays digest-only until the false-positive rate is confirmed low on real usage.

Delivery script and install command: `openclaw/notifier/README.md`. Runs as an `openclaw cron --command` job (`fieldops-notifier`, every 1 minute) — same cron store as the digest jobs, same "won't survive a Pi reprovision, recreate with the documented command" caveat.

**Shift-confirmation nudges (2026-08-12):** a separate script/cron job (`fieldops-shift-nudge`, once daily at 6pm) messages each crew member directly — not management — whose shift for tomorrow is still unconfirmed, asking them to reply CONFIRM or DECLINE (routed to the existing `confirm_shift` tool, no new agent logic needed). See `openclaw/notifier/README.md`.

**Safety incidents (2026-08-13):** the one notification the agent authors itself mid-conversation rather than the backend deriving from state. If a message sounds like an injury or on-site danger, `AGENTS.md`'s "Safety and emergencies" section (positioned above the confirm-before-execute rule, deliberately) has the agent tell the sender to call 911 immediately, then call `report_safety_incident` — no confirmation step, straight into the same critical-notification pipeline as everything else, delivered within the minute like any other critical push.

## Live vehicle location

Unlike `fieldops-media` (a hook plugin), this is **agent-driven, not hook-driven** — confirmed by tracing OpenClaw's actual source before building anything. Media attachments get a dedicated `mediaPath`/`mediaType` field threaded all the way through `deriveInboundMessageHookContext` → `toPluginMessageReceivedEvent`/`toInternalMessageReceivedContext` into `event.metadata`, so a `message:received` hook can see them. WhatsApp location shares don't: `toLocationContext` (in `openclaw/plugin-sdk/channel-inbound`) produces `LocationLat`/`LocationLon`/etc., but those are documented as "template context fields for prompt metadata" — they only feed the text the *agent* sees (`📍 lat, lon` appended to the message body via `formatLocationText`), and grepping the compiled hook-mapper source confirms they never reach `event.metadata`. A hook-only plugin like `fieldops-media` genuinely can't see a location share; only the agent can, from the message text.

So this is built as an agent instruction, not a plugin: `AGENTS.md`'s new "Live vehicle location" section teaches the agent to recognize the `📍`/`🛰` coordinate line in a message, resolve the sender to a crew member (existing pattern), call the new `list_vehicles` tool with `assigned_crew_id` to find their vehicle, and call the existing `log_vehicle_location` tool — explicitly **without confirmation**, since it's passive telemetry the crew member already chose to send, not a decision being made on their behalf.

This needed three new tools/endpoints that didn't exist before (same gap crew-members/sites had — nothing could look up or register a vehicle at all): `GET /vehicles?assigned_crew_id=&plate=`, `GET /vehicles/:id` (returns `latest_location`, the most recent telemetry row), and `POST /vehicles`. Verified end to end against the live backend: registered a test vehicle assigned to a test crew member, confirmed the `assigned_crew_id` filter resolves it, logged telemetry, confirmed `latest_location` populates on the detail endpoint, and confirmed the 404/empty-filter/validation edge cases. Test data cleaned up after.

**Reverse geocoding (2026-08-12):** `POST /vehicles/:id/telemetry` now resolves raw lat/lng into a real address (e.g. "45 O'Connor Street, Ottawa") via OpenStreetMap Nominatim — free, no API key. To respect Nominatim's 1 req/sec usage policy, a new point within ~100m of the vehicle's last geocoded point reuses that address instead of re-geocoding (`backend/src/lib/geocode.ts`, `metersBetween`) — matters for live-location shares that can ping every few minutes without the vehicle actually moving. Geocoding failures (timeout, Nominatim down) never block logging the coordinates — `address` is just null. Verified against real coordinates: a nearby point correctly reused the prior address, a ~2km-away point correctly re-geocoded to a different real address, and `get_vehicle`'s `latest_location.address` reflects it. Both `log_vehicle_location` and `get_vehicle` tool descriptions, and `AGENTS.md`, now steer the agent to relay the address, not raw coordinates.
